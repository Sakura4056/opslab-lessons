# 故障排查四套话术

> 阶段笔记：[[阶段6_求职冲刺]] ｜ 上一讲：[[阶段6_求职冲刺/01_面试八股速览|面试八股速览]] ｜ 下一讲：[[阶段6_求职冲刺/03_简历与面试指南|简历与面试指南]]
> 面试必考：「网站变慢你怎么处理？」——考察的不是命令，是**有序的排查思维**。每套话术 = 分层定位 + 常用命令 + 处置动作。四套都要在 WSL 里实际演练过。

## 通用开场（每套都用）

1. **确认现象**：范围（全部/部分用户？）、时间点（何时开始？有无变更？）、影响面；
2. **分层定位**：网络 → 系统 → 应用 → 依赖；
3. **先止血后根因**：能重启/回滚先恢复业务，保留现场再深挖。

## 套路一：网站变慢 / 无法访问

```
① 检查自己能不能复现：curl -w 状态码+耗时
② 网络层：ping/traceroute 分段；DNS 解析对不对
③ 系统层：top(CPU) → free(内存) → df -h(磁盘) → iostat(IO)
④ 应用层：nginx access/error 日志 → 慢请求在什么接口 → upstream 状态
⑤ 依赖层：数据库/缓存慢查询（slow log）→ 联动开发
处置：扩容/限流/重启依赖，恢复后写复盘
```

**命令**：`curl -sS -o /dev/null -w "%{http_code} %{time_total}\n"`、`top`、`df -h`、`ss -tan | awk '{print $1}' | sort | uniq -c`。

## 套路二：CPU 飙高 100%

```
① top → P 排序锁定进程
② 进程内定位：top -H -p PID 看线程 / 或 strace -p PID 抓系统调用
③ 常见根因：死循环、正则回溯、GC 频繁、进程数暴涨
④ 处置：确认业务后重启进程；代码问题转开发
```

**命令**：`ps aux --sort=-%cpu | head`、`top -H -p PID`、`pidstat -u 1`。

## 套路三：磁盘满

```
① df -h 找满的挂载点 → du -sh /* 逐层下钻找大目录
② 高频元凶：日志疯长、core dump、docker 镜像堆积、数据库 binlog
③ 处置：日志清理(确认后)/docker system prune/rotate binlog
④ 根治：logrotate 配置、监控告警（85% 告警线）
```

**命令**：`df -h`、`du -xh --max-depth=2 /`、`docker system df`；**注意**：删除被进程占用的文件不释放空间 → `lsof | grep deleted` → 重启对应进程。

## 套路四：端口不通 / 连接超时

```
① 分层：ping IP → dig 域名 → nc -zv 端口 → curl 应用
② 本机监听：ss -tlnp 看服务是否 LISTEN
③ 中间层：防火墙 ufw status / 云安全组 / 负载均衡健康检查
④ 处置：按层修复（服务起/防火墙放行/安全组加规则）
```

**命令**：`ss -tlnp`、`nc -zv host port`、`sudo ufw status`、`journalctl -u 服务名`。

## 动手实验（每套都亲手制造一次故障）

- [ ] CPU 飙高：`while true; do :; done &` → top 定位 → kill
- [ ] 磁盘满（WSL 演练）：`fallocate -l 5G bigfile` → df/du 定位 → 删除
- [ ] 端口不通：stop nginx → nc 探测失败 → start 恢复
- [ ] 网站变慢：给 app.py 加 `time.sleep(2)` → curl 耗时变化 → 定位 → 恢复
- [ ] 四套话术各写成 Markdown 存入 `05_References\速查手册\故障排查\`

## 常见坑（面试表达层面）

- **上来就报命令**：先讲思路框架再讲命令，面试官要的是有序性；
- **不会说「不知道」**：超出范围时讲「我会按 XX 思路去定位」比胡编强；
- **没提「保留现场」**：生产故障先止血但留存证据（日志/截图），体现工程素养；
- **没提复盘**：结尾补一句「事后写复盘、补监控告警」，闭环。

## 自测

1. 四套话术各自的第一步是什么？共同的开场三问是什么？
2. 磁盘满删除文件后空间没释放，为什么？怎么查？
3. CPU 飙高如何从进程定位到线程再到代码？
4. 「网站变慢」如何区分是网络问题还是应用问题？
